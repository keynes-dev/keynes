Baseline: `d030ba2ff11601d26b7c83d2e2c85c42840c1bbc`, 2026-09-23. All 36 existing feature directories are accounted for below. This COR-131 directory is new and excluded from the baseline count. Topic boundaries are defined once in [the ownership contract](contracts/documentation-ownership.md); work labels refer to [bounded proposals](work-proposals.md).

This inventory classifies subjects, not release readiness. A mixed directory can contain current rules, superseded proposals and valid historical evidence. Before removal, expand its row into a section/requirement-level relocation ledger and verify each item against current source/tests. A blanket directory move is not acceptance.

## Coverage protocol before removing a directory

1. Enumerate its spec requirements, contracts, rationale, quickstart/examples, accepted commitments and evidence. Record each source path/section at a full SHA.
2. Give each item a current permanent destination, explicit future-commitment destination, or historical/retired reason. Superseded behavior is never promoted merely to avoid a gap.
3. Compare current exported APIs, canonical operations, tests, documented limits and ADR decisions with those rows. Add missing behavior not described in old plans.
4. Reconcile contradictions. If source and an accepted contract differ, record the discrepancy and resolve it through review; do not silently rewrite product meaning as a documentation migration.
5. Replace active inbound links and executable dependencies. Historical references use a publicly reachable full SHA, with contextual notes for already-broken ADR paths.
6. Run the owning examples, type/package checks where imports or archive contents change, and the retention/link gates. Retain essential reports before deleting temporary files.

No legacy directory is approved for deletion by this inventory. Publication findings stay in their internal owning issue. A historical path's presence here does not clear its contents for public release.
