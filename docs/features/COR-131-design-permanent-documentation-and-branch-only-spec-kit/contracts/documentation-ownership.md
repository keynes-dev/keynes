# Proposed documentation ownership contract

Status: design for review. Paths marked new do not exist yet. This document owns the proposed allocation of topics; it does not redefine the product's contracts.

## One owner per topic

`docs/README.md` is the maintained navigation and ownership index. A page names its audience, scope, and links to adjacent owners. It may summarize another topic but cannot add independent rules, signatures, error enumerations, numeric limits, or qualification claims for that topic.

Every supported behavior has reference documentation explaining inputs, outputs, validation order, failures, state effects, retry/lifecycle behavior, limits and compatibility where relevant. Every material choice has an explanation or ADR link. A behavior checklist is coverage evidence, not another copy of the rule. Generated types/schemas remain canonical for machine structure. Prose must explain meaning and consequences the machine source cannot express.

## Placement rule

Choose the location by the topic's owner, not by how many documents mention it:

- Centralize product vision, architecture, shared Budget/accounting/command semantics, contributor workflow, repository testing, release procedures and cross-package ADRs under `docs/`.
- Colocate a package's public API, configuration, validation, errors, lifecycle, limits and runnable examples in its `README.md` and focused `docs/` pages. The CLI follows the same rule under `apps/cli/`.
- Keep `docs/README.md` as the navigation and topic-ownership index across both locations. A central index does not require centralized content.
- Explain package-local choices beside the owning contract. Record current architectural choices affecting multiple packages in `docs/adr/`, and link to them from the affected package docs. Retain replaced ADR bodies as exact records in pinned main history after their active rationale moves to a current owner.

Settlement and conservation belong in the shared accounting reference. Borrowed PostgreSQL transaction ownership belongs in the PostgreSQL package. TypeScript result types belong in the SDK. A rule implemented by one package remains package-owned even when other packages consume it; those consumers link to its definition.

SDK, PostgreSQL and Policy need focused package-local pages for their established subjects. SQLite and CLI initially keep their smaller references in their READMEs. Database and testkit keep contributor documentation beside their implementation. Split a README only when its existing subjects warrant separate pages.

## Examples, packaging, and links

Keep runnable examples with the package they teach. Reuse `packages/policy/test/fixtures/policy-scenarios.ts`, its Vitest/native tests, and existing SDK/package smoke checks. Extract a shared example module only if documentation execution requires it; do not clone fixture logic into a new example framework. The KEY-118 sketches do not introduce a public runner API.

The root quickstart is a convenience excerpt from a tested Local example. Package guides point to runnable files, expected observations, and relevant contracts. No example depends on a temporary feature path, private source or infrastructure, embedded secrets, or a live provider. PostgreSQL examples may use environment-supplied credentials from their documented disposable fixture setup and must state those prerequisites. They must not require access to private services or existing customer credentials.

Package READMEs ship in archives. If a README links to new local `docs/` files, add those files to that package's `files` allowlist and check the resulting archive. Cross-repository links must target the approved public, release-pinned source or documentation URL; do not pretend `../../docs` resolves inside a standalone archive. Before public publication, repository-relative links are valid only in the repository and must be labeled or repaired in packaged documentation. No docs duplication solely to work around a link.

Current rules link to permanent relative paths. Historical citations link to full-SHA URLs that remain publicly reachable. Existing broken links are an explicit migration backlog, including old ADR feature paths. Do not rewrite a historical ADR body. When consolidation removes one from HEAD, migrate its active rationale, preserve its exact bytes at a pinned retained revision, and map it from the current ADR index.

Before removing a feature directory, follow the [migration coverage protocol](../migration-map.md#coverage-protocol-before-removing-a-directory).
